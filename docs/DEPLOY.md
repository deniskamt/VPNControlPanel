# Установка панели на сервер

Панель — обычное веб-приложение: Python-процесс за nginx плюс Postgres.
Держать её на VPN-сервере не обязательно и не нужно: она управляет нодами
по сети, а сама может стоять где угодно.

**Что понадобится**

- сервер с Ubuntu 22.04/24.04 или Debian 12, 1 vCPU и 1 ГБ RAM хватит
  (панель не гоняет трафик пользователей, только управляет нодами);
- домен, направленный A-записью на этот сервер;
- **тот самый домен, на котором сейчас работают подписки Marzban**
  (`nexlovpn.online`) — его тоже нужно перенаправить на панель, иначе
  выданные пользователям ссылки перестанут открываться.

Домены могут быть разными: например, `panel.nexlovpn.online` для админки и
`nexlovpn.online` для подписок. Оба должны вести на этот сервер.

## Пробная установка на одном сервере (без домена)

Чтобы просто посмотреть, как всё работает, домен не нужен: панель поднимется
по IP, а REALITY не требует сертификата. Панель и нода могут жить на одной
машине. Годится для проверки, но **не для боевого запуска** — по http пароль
и токены идут открытым текстом.

**1. Поставить панель**

```bash
apt update && apt install -y git
git clone https://github.com/deniskamt/VPNControlPanel.git /opt/vpn-panel
cd /opt/vpn-panel
bash scripts/install_panel.sh
```

На вопрос «Домен или IP панели» ответьте IP сервера. Скрипт увидит, что это
не домен, перейдёт на `http`, поднимет панель на всех интерфейсах и не станет
ждать nginx. Остальные вопросы можно проматывать Enter'ом. В конце он напечатает
адрес входа и пароль.

**2. Открыть порт**

```bash
ufw allow from <ваш домашний IP> to any port 8000 proto tcp   # безопаснее
# или, если IP плавающий:
ufw allow 8000/tcp
```

Заходим на `http://<IP сервера>:8000`.

**3. Добавить сервер и поставить агента**

«Серверы» → «Добавить сервер»:

- **Название** — любое, попадёт в имя профиля у клиента;
- **Адрес для клиентов** — IP сервера;
- **Адрес агента** — `127.0.0.1`, если панель и нода на одной машине
  (тогда порт агента наружу открывать не нужно);
- **Токен агента** — уже подставлен, скопируйте его.

Сохраните, затем выполните на сервере команду из блока внизу страницы:

```bash
curl -fsSL http://<IP сервера>:8000/install/install_agent.sh -o install_agent.sh
AGENT_TOKEN=<токен из формы> PANEL_URL=http://<IP сервера>:8000 bash install_agent.sh
```

Скрипт поставит Xray-core и агента. Сервер пока будет красным — inbound'ов
ещё нет, это нормально.

**4. Создать подключение**

«Подключения» → шаблон **VLESS + REALITY + XHTTP** (предлагается первым) →
«Создать подключение». Ключи, shortId, путь и маскировку панель сгенерирует
сама, JSON писать не нужно. Из полей имеет смысл трогать только маскировочный
домен — под него подключение будет притворяться.

Подключение сразу поднимается на всех включённых серверах и попадает в
подписки пользователей; выбрать конкретные серверы можно галочками.

Порт 443 на сервере должен быть свободен; если занят, укажите другой.

**Какой шаблон брать.** Коротко, под российские сети 2026 года:

| Шаблон | Когда |
| --- | --- |
| VLESS + REALITY + XHTTP | по умолчанию: трафик разложен по обычным HTTP-запросам и не попадает под «заморозку» соединения после ~16 КБ |
| VLESS + REALITY + Vision | быстрее всех (XTLS), хорошо у проводных провайдеров; на мобильных чаще упирается в ту самую «заморозку» |
| VLESS + REALITY + gRPC | запасной транспорт, когда придушен обычный TCP |
| VLESS + XHTTP за CDN | сети, где прямое соединение с зарубежным сервером не устанавливается: трафик идёт через Cloudflare |
| Shadowsocks 2022 | запасной канал вообще без TLS |

**Подключение не появилось в приложении.** Две причины, обе раньше молчали:

* у пользователя нет ключа нужного протокола. Trojan и Shadowsocks — это
  пароль, а не UUID: подключение отмечено, а собрать ссылку не из чего.
  Теперь ключ выдаётся сам, как только подключение отмечено у пользователя;
* подключение никому не выдано. Новое подключение теперь достаётся всем
  пользователям сразу; созданным раньше поможет кнопка **«Выдать всем»** в
  строке подключения.

Отдельно: если подключение помечено предупреждением про усиленную маскировку,
оно не будет работать у части пользователей — уберите поля `xPadding*`,
`seqKey`, `sessionID*` в «Настроить».

Одного подключения обычно мало: полезно поднять два-три разных транспорта —
клиент покажет их списком, и пользователь переключится, если сеть придушила
один из них.

**Режим XHTTP** панель ставит сама — `packet-up`, и это важнее, чем кажется.
Под REALITY режим `auto` выбирает `stream-one`, то есть **один длинный
поток**: под «заморозку» после ~16 КБ он подпадает ровно так же, как обычный
VLESS, и весь смысл XHTTP теряется. При `packet-up` аплинк уходит отдельными
запросами.

Вместе с режимом панель кладёт параметры дробления соединений:

| Параметр | Зачем |
| --- | --- |
| `scMaxEachPostBytes` | ограничивает, сколько данных несёт один запрос |
| `scMinPostsIntervalMs` | пауза между запросами, чтобы не выглядеть роботом |
| `scStreamUpServerSecs` | периодически пересоздаёт даунлинк |
| `xmux.cMaxReuseTimes`, `hMaxRequestTimes` | сколько раз переиспользовать соединение, прежде чем открыть новое |

Они едут клиенту в ссылке полем `extra`. Проверено на живых ядрах: понимают
и 25.6.8, и 26.3.27, и 26.7.28; скорость от дробления не падает.

**Усиленная маскировка XHTTP** (`xPadding*`, `seqKey`, `sessionID*`) из
панели убрана. Поля настоящие и ядром применяются, но совместимы только между
**одинаковыми версиями ядра**: замер на живых сборках дал такую картину —
сервер 26.3.27 работает с клиентом 26.3.27, но не с 26.7.28 и не с 25.6.8.
Версия ядра внутри приложения меняется сама по себе, поэтому подключение
работало бы у одних пользователей и молчало у других. Если поля всё-таки
нужны, их можно вписать вручную через «Создать вручную» — панель пометит
такое подключение предупреждением.

**minClientVer панель не выставляет** — и не должна. Проверка в исходниках
REALITY:

```go
config.MinClientVer == nil || Value(ClientVer) >= Value(MinClientVer)
```

Без поля проверки версии нет вообще. С полем клиент обязан прислать версию
своего ядра, а реализации не на Xray шлют нули — сервер молча отдаёт их
маскировочному сайту. Рукопожатие при этом проходит, поэтому со стороны это
выглядит как «подключение есть, интернета нет». Поле не переносится на ноду,
даже если осталось в настройках от прежних версий панели.

Чего в наборе нет: AmneziaWG работает поверх UDP и требует другого ядра —
агент управляет Xray и Hysteria2. VMess и обычный TLS оставлены только в
«устаревших».

Панель сама зальёт конфиг, и через несколько секунд сервер станет зелёным.
Если нет — кнопка «Конфиг» в строке сервера покажет, что именно уехало на
ноду, а «Журнал» — что не понравилось Xray.

**5. Проверить**

«Пользователи» → «Добавить пользователя» → открыть карточку. Там ссылка
подписки и QR-код: в v2rayNG, NekoBox или Hiddify её добавляют **как
подписку**, а не как отдельный сервер. QR проще — сканируется камерой прямо
из приложения.

Когда наиграетесь — берите домен, ставьте nginx с сертификатом и меняйте
`PANEL_URL` и `SUBSCRIPTION_BASE_URL` в `.env` на `https://...`.

## Быстрый путь (скрипт)

```bash
apt update && apt install -y git
git clone https://github.com/deniskamt/VPNControlPanel.git /opt/vpn-panel
cd /opt/vpn-panel
bash scripts/install_panel.sh
```

Скрипт спросит домены и сделает всё сам: поставит Postgres, создаст базу и
пользователя со случайным паролем, соберёт виртуальное окружение, сгенерирует
`.env` с ключами, поднимет systemd-сервис `vpn-panel` на `127.0.0.1:8000`.
В конце он напечатает логин и пароль администратора — **сохраните их сразу**,
второй раз пароль не показывается.

Дальше остаётся [настроить nginx и сертификат](#nginx-и-сертификат).

## Ручной путь

Если хочется понимать каждый шаг или сервер нестандартный.

### 1. Пакеты

```bash
apt update
apt install -y python3 python3-venv python3-dev build-essential \
               postgresql nginx certbot python3-certbot-nginx git curl
```

### 2. База данных

```bash
systemctl enable --now postgresql

su - postgres -c "psql -c \"CREATE ROLE vpnpanel WITH LOGIN PASSWORD 'ПРИДУМАЙТЕ_ПАРОЛЬ';\""
su - postgres -c "createdb -O vpnpanel vpnpanel"
```

### 3. Код и окружение

```bash
git clone https://github.com/deniskamt/VPNControlPanel.git /opt/vpn-panel
cd /opt/vpn-panel

python3 -m venv .venv
.venv/bin/pip install --upgrade pip
.venv/bin/pip install -r requirements.txt
```

### 4. Настройки

```bash
cp .env.example .env
python3 -c "import secrets; print(secrets.token_urlsafe(48))"   # для SECRET_KEY
nano .env
chmod 600 .env
```

Минимум, что нужно заполнить:

```ini
SECRET_KEY=<длинная случайная строка>
PANEL_URL=https://panel.nexlovpn.online
DATABASE_URL=postgresql://vpnpanel:ПАРОЛЬ@127.0.0.1:5432/vpnpanel

ADMIN_USERNAME=admin
ADMIN_PASSWORD=<пароль для первого входа>

SUBSCRIPTION_BASE_URL=https://nexlovpn.online   # домен, который уже у пользователей
SUBSCRIPTION_PATH=c                             # префикс пути, как в Marzban
SUBSCRIPTION_SECRET=                            # заполняется на шаге миграции
```

`SUBSCRIPTION_BASE_URL` и `SUBSCRIPTION_PATH` должны в точности совпадать с
тем, что было в Marzban, — из них складывается ссылка, которая уже лежит
в приложениях у пользователей.

Администратор создаётся при первом запуске и только если в базе нет ни
одного админа. Менять `ADMIN_PASSWORD` потом бессмысленно — пароль уже в базе.

### 5. Автозапуск

```bash
cat > /etc/systemd/system/vpn-panel.service <<'EOF'
[Unit]
Description=VPN Control Panel
After=network.target postgresql.service

[Service]
Type=simple
WorkingDirectory=/opt/vpn-panel
EnvironmentFile=/opt/vpn-panel/.env
ExecStart=/opt/vpn-panel/.venv/bin/uvicorn app.main:app \
    --host 127.0.0.1 --port 8000 \
    --proxy-headers --forwarded-allow-ips '*'
Restart=always
RestartSec=5
LimitNOFILE=1048576

[Install]
WantedBy=multi-user.target
EOF

systemctl daemon-reload
systemctl enable --now vpn-panel
systemctl status vpn-panel
```

Панель намеренно слушает только `127.0.0.1` — наружу её пускает nginx.

## Nginx и сертификат

Одной командой:

```bash
cd /opt/vpn-panel
bash scripts/setup_domain.sh vixar.fun --email you@example.com
```

Скрипт проверит, что порт 443 свободен и домен указывает на этот сервер,
поставит nginx и certbot, получит сертификат, пропишет https-адреса в `.env`
и уберёт панель с внешнего интерфейса — снаружи останется только nginx.
Домен подписок задаётся отдельно: `--sub nexlovpn.online`.

**Порт 443 придётся делить.** Если панель и VPN на одной машине, оба не могут
слушать 443. Скрипт это заметит и остановится. Обычно проще перенести
подключение на другой порт («Подключения» → «Настроить» → порт 8443):
ссылки у пользователей обновятся сами при следующем обновлении подписки.

**Cloudflare.** На время выпуска сертификата запись домена должна стоять в
режиме **DNS only** (серое облако) — с проксированием certbot часто не
проходит. После выпуска оранжевое облако можно вернуть, но режим SSL/TLS
обязательно **Full (strict)**, иначе получится цикл редиректов.
Адрес VPN-серверов через Cloudflare не проксируется никогда: для нод
используйте IP или отдельную запись с серым облаком.

### Вручную

```bash
cat > /etc/nginx/sites-available/vpn-panel <<'EOF'
server {
    listen 80;
    listen [::]:80;
    server_name panel.nexlovpn.online nexlovpn.online;

    location / {
        proxy_pass http://127.0.0.1:8000;
        proxy_http_version 1.1;
        proxy_set_header Host              $host;
        proxy_set_header X-Real-IP         $remote_addr;
        proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_read_timeout 60s;
    }
}
EOF

ln -sf /etc/nginx/sites-available/vpn-panel /etc/nginx/sites-enabled/
rm -f /etc/nginx/sites-enabled/default
nginx -t && systemctl reload nginx
```

Сертификат — certbot сам перепишет конфиг под HTTPS и настроит редирект:

```bash
certbot --nginx -d panel.nexlovpn.online -d nexlovpn.online
```

Заголовок `X-Forwarded-Proto` обязателен: по нему панель понимает, что
работает по HTTPS, и ставит cookie сессии с флагом `Secure`.

Проверка:

```bash
curl -s https://panel.nexlovpn.online/healthz     # {"status":"ok"}
```

## Раздача через сервер из белых списков

Бывает, что адрес ноды у провайдеров не проходит, а адрес другого сервера —
проходит. Тогда клиентам дают адрес этого сервера, а он передаёт соединение
ноде. В панели это делается одной строкой подписки: «Подписка» → «Настроить»
→ **Адрес** = адрес переднего сервера. SNI, порт и ключи не трогаем — они
принадлежат ноде.

**Обычный обратный прокси для этого не годится.** REALITY — это и есть TLS:
клиент здоровается с нодой, а нода отвечает ему своим рукопожатием. Если на
переднем сервере стоит `proxy_pass` внутри `http {}`, то nginx ответит
клиенту сам, своим сертификатом, — и клиент оборвёт соединение, даже не дойдя
до ноды. То же и с Cloudflare: он тоже терминирует TLS.

Передний сервер должен отдать соединение **байт в байт**. Это `stream`
с `ssl_preread`: nginx подсматривает имя домена в первом пакете и по нему
выбирает, куда отправить поток, не разбирая ничего дальше.

```nginx
# /etc/nginx/nginx.conf — рядом с http {}, не внутри него
stream {
    map $ssl_preread_server_name $upstream {
        sub.nexlovpn.online    127.0.0.1:8443;      # панель — её TLS терминирует сам nginx
        www.lovelive-anime.jp  78.17.173.142:443;   # маскировочный домен ноды — насквозь
        default                127.0.0.1:8443;
    }

    server {
        listen 443;
        listen [::]:443;
        ssl_preread on;
        proxy_pass $upstream;
    }
}
```

Слева в `map` — маскировочный домен подключения (`serverNames` у REALITY,
он же `sni=` в ссылке), справа — адрес и порт ноды. Один домен на одну ноду:
по нему nginx их и различает.

Порт 443 при этом занимает `stream`, поэтому http-сервер панели должен уйти
с него на локальный адрес:

```nginx
server {
    listen 127.0.0.1:8443 ssl;
    http2 on;
    server_name sub.nexlovpn.online;
    # ...остальное без изменений
}
```

Проверка — с любой машины:

```bash
openssl s_client -connect <передний сервер>:443 -servername www.lovelive-anime.jp </dev/null 2>/dev/null | openssl x509 -noout -subject
```

REALITY на чужое рукопожатие отвечает настоящим сертификатом маскировочного
домена. Поэтому `subject` с `www.lovelive-anime.jp` означает, что поток
доходит до ноды. Свой домен в ответе — значит, отвечает nginx, и до ноды
ничего не доехало.

Что важно помнить:

* **счётчик устройств перестаёт работать** для этой строки: ноде все
  подключения приходят с одного адреса — переднего сервера;
* **Hysteria2 так не пробросить**: это UDP, `ssl_preread` к нему неприменим.
  Нужен отдельный `server { listen <порт> udp; proxy_pass <нода>:<порт>; }`
  на своём порту — простая пересылка, без разбора имени;
* если на ноде файрвол ограничивает 443, откройте его для адреса переднего
  сервера.

## Файрвол

```bash
ufw allow 22/tcp
ufw allow 80,443/tcp
ufw enable
```

Порт агента (8443) на **нодах** должен быть открыт только для адреса панели:

```bash
# на каждом VPN-сервере
ufw allow from <IP панели> to any port 8443 proto tcp
ufw deny 8443/tcp
```

Токен агента — единственное, что защищает ноду от постороннего управления,
поэтому ограничение по IP здесь не формальность.

### Перенос на тестовую панель

Прежде чем трогать боевую, базу Marzban полезно скопировать на тестовую
панель и посмотреть на живых данных: те ли пользователи, те ли ссылки, что
показывает клиент. Боевой Marzban при этом не трогается вообще — читается
только копия его базы.

Дальше два разных сервера. Команды **не** выполняются подряд в одном
терминале: сначала всё на сервере Marzban, потом всё на сервере панели.

#### Шаг 1 — на сервере Marzban

Снять копию базы (боевой Marzban при этом продолжает работать) и отправить её
на панель. `panel.example.com` замените на адрес своей панели:

```bash
apt install -y sqlite3                       # если ещё нет
sqlite3 /var/lib/marzban/db.sqlite3 ".backup /tmp/marzban-copy.sqlite3"
ls -lh /tmp/marzban-copy.sqlite3             # файл должен появиться

scp /tmp/marzban-copy.sqlite3     root@panel.example.com:/opt/vpn-panel/marzban.sqlite3
scp /var/lib/marzban/xray_config.json root@panel.example.com:/opt/vpn-panel/
```

Если Marzban на MySQL, вместо первой команды:

```bash
mysqldump -u root -p marzban | gzip > /tmp/marzban.sql.gz
```

— и разверните дамп в MySQL уже на панели, а в `--source` укажите
`mysql+pymysql://...`.

Копия базы — это ключи всех пользователей. Держите её только на время
проверки и потом удалите с обоих серверов.

#### Шаг 2 — на сервере панели

```bash
ssh root@panel.example.com
cd /opt/vpn-panel
ls -lh marzban.sqlite3                       # файл доехал?

.venv/bin/pip install -r requirements-migrate.txt

.venv/bin/python scripts/migrate_from_marzban.py \
    --source "sqlite:////opt/vpn-panel/marzban.sqlite3" \
    --xray-config /opt/vpn-panel/xray_config.json \
    --dry-run
```

Четыре слеша в `sqlite:////` не опечатка: три от схемы плюс корневой слеш
абсолютного пути.

Скрипт ничего не пишет и печатает, что перенесётся, а также строку
`SUBSCRIPTION_SECRET=...` — секрет подписи из Marzban.

#### Шаг 3 — там же, на сервере панели

Прописать секрет и перенести. Без совпадающего секрета ссылки подписок
открываться не будут — на тестовой панели это первое, что стоит проверить.

```bash
.venv/bin/python scripts/migrate_from_marzban.py \
    --source "sqlite:////opt/vpn-panel/marzban.sqlite3" \
    --xray-config /opt/vpn-panel/xray_config.json \
    --write-env \
    --limit 20

systemctl restart vpn-panel
```

`--write-env` сам пропишет `SUBSCRIPTION_SECRET` в `.env` (прежний файл
сохраняется рядом как `.env.bak`) — редактор для этого не нужен. Повторный
запуск ничего не портит: если секрет уже такой, файл не трогается.

`--limit 20` берёт только первых двадцать пользователей: для проверки этого
достаточно, а база остаётся обозримой. Без него переносятся все.

#### Шаг 4 — что проверить в панели

| Проверка | Как |
| --- | --- |
| пользователи на месте | «Пользователи» — статусы, трафик, сроки как в Marzban |
| ключи не поменялись | открыть карточку, сверить UUID с тем, что в Marzban |
| ссылка живёт | взять у пользователя старую ссылку подписки из Marzban и открыть её на тестовой панели — она обязана отдать конфиги |
| подключения | «Подключения» — перенеслись теги; порт и ключи подставятся из `xray_config.json` |
| REALITY | `publicKey` панель вычисляет из приватного сама — сверено с выводом `xray x25519` |

Проверено на синтетической базе Marzban: пользователи со статусами, трафиком
и UUID переносятся один в один, а токен подписки, который выдаёт панель,
побайтово совпадает с тем, что выдавал Marzban.

**Важно про тестовую панель.** Её домен должен отличаться от боевого, иначе
клиенты пользователей начнут ходить за подписками к ней. Ноды переносятся
выключенными — тестовая панель не пойдёт настраивать боевые серверы, пока вы
сами их не включите и не поставите на них агента.

## Перенос данных из Marzban

Делается один раз, после того как панель поднялась.

```bash
cd /opt/vpn-panel
.venv/bin/pip install -r requirements-migrate.txt

.venv/bin/python scripts/migrate_from_marzban.py \
    --source "sqlite:////var/lib/marzban/db.sqlite3" \
    --xray-config /var/lib/marzban/xray_config.json \
    --dry-run
```

Для MySQL: `--source "mysql+pymysql://user:pass@127.0.0.1/marzban"`.
Если Marzban на другом сервере — снимите дамп и положите файл рядом, либо
откройте доступ к его базе с адреса панели.

Скрипт напечатает строку вида `SUBSCRIPTION_SECRET=...`. Впишите её в `.env`
и перезапустите панель:

```bash
nano .env                        # SUBSCRIPTION_SECRET=<из вывода скрипта>
systemctl restart vpn-panel
```

Затем прогоните перенос уже без `--dry-run`. Скрипт идемпотентен: перед
самым переключением домена его можно запустить ещё раз, чтобы догнать
оплаты, прошедшие за время подготовки.

После переноса зайдите в панель → «Подключения» и впишите `publicKey` для
REALITY: в серверном конфиге его нет, он получается на ноде командой
`xray x25519 -i <privateKey>`. Без него клиенты не подключатся.

## Подключение серверов

В панели: «Серверы» → «Добавить сервер». Скопируйте команду из блока внизу
страницы и выполните её на VPN-сервере под root:

```bash
curl -fsSL https://panel.nexlovpn.online/install/install_agent.sh -o install_agent.sh
AGENT_TOKEN=<токен из формы> PANEL_URL=https://panel.nexlovpn.online bash install_agent.sh
```

Скрипт ставит Xray-core и агента, поднимает сервис `vpn-agent`. Через
полминуты сервер в панели станет зелёным, и конфиг уедет на него сам.

Панель и нода могут жить на одном сервере — тогда в поле «Адрес агента»
укажите `127.0.0.1`, и порт наружу открывать вообще не нужно.

## Проверка перед переключением

1. Заведите тестового пользователя, откройте его ссылку подписки, подключитесь.
2. Возьмите **старую** ссылку реального пользователя (из Marzban) и откройте

### Панель уже стоит — что делать дальше

Переустанавливать её ради изменений не нужно. Смотря что требуется:

Все команды ниже выполняются в каталоге, куда панель установлена. Скрипт
ставит её туда, откуда его запустили, — `/opt/vpn-panel` в инструкции просто
пример. Если забыли, куда именно:

```bash
systemctl cat vpn-panel | grep WorkingDirectory
```

| Задача | Что сделать |
| --- | --- |
| не помню, куда поставил | `systemctl cat vpn-panel \| grep WorkingDirectory` |
| поменять адрес, домен, токен бота и прочие настройки | `nano .env` → `systemctl restart vpn-panel` |
| обновить код панели | `git pull` → `pip install -r requirements.txt` → `systemctl restart vpn-panel` |
| забыт пароль администратора | `.venv/bin/python scripts/admin.py set-password --username admin` |
| завести второго администратора | `.venv/bin/python scripts/admin.py set-password --username operator` |
| посмотреть, кто есть | `.venv/bin/python scripts/admin.py list` |
| узнать команду установки агента | `.venv/bin/python scripts/node.py install` |
| перевести панель на домен и HTTPS | `bash scripts/setup_domain.sh <домен>` |
| «локально работает, из браузера нет» | `bash scripts/diagnose.sh` |
| оформление подписки в приложении | «Настройки» → «Как подписка выглядит в приложении» |
| перевыпустить ключи, оставив данные | `REINSTALL=1 bash scripts/install_panel.sh` (см. предупреждение ниже) |
| снести панель полностью | `bash scripts/uninstall_panel.sh` |

Скрипт установки можно запускать повторно — он увидит существующий `.env` и
переведёт себя в режим обновления: сохранит `SECRET_KEY`, `SUBSCRIPTION_SECRET`,
доступ к базе, пароль администратора и правки в настройках, обновив только
зависимости и systemd-сервис. Пароль при этом не печатается: он хранится в
базе, и переменная `ADMIN_PASSWORD` на него уже не влияет — она срабатывает
единственный раз, когда админов ещё нет.

**`REINSTALL=1` перевыпускает `SECRET_KEY`.** Если `SUBSCRIPTION_SECRET` не
задан явно, токены подписок подписываются именно им — значит, все выданные
пользователям ссылки перестанут открываться. Данные в базе при этом
сохраняются, но подписки придётся раздавать заново.

### Снести и поставить заново

Для пробной установки, которую не жалко, проще всего начать с нуля:

```bash
bash scripts/uninstall_panel.sh          # спросит про базу и исходники
```

Скрипт сам находит каталог установки по systemd-юниту, останавливает и
удаляет сервис, сносит окружение и `.env`. Базу и исходники он трогает
только с вашего согласия — по умолчанию оставляет.

Снести вообще всё, не отвечая на вопросы:

```bash
DROP_DATABASE=1 PURGE=1 bash scripts/uninstall_panel.sh -y
```

Затем обычная установка:

```bash
git clone https://github.com/deniskamt/VPNControlPanel.git /opt/vpn-panel
cd /opt/vpn-panel
bash scripts/install_panel.sh
```

Агенты на нодах при этом остаются жить своей жизнью. Если сносите и их:

```bash
# на каждом VPN-сервере
systemctl disable --now vpn-agent && rm -rf /opt/vpn-agent
```

### Сервер горит красным: «нет связи с агентом»

Панель не смогла достучаться до агента. Причин ровно три, и панель теперь
подсказывает нужную прямо в строке сервера.

**1. Агент не установлен или не запущен.** Самое частое: сервер добавили,
а команду установки не выполнили. На сервере:

```bash
systemctl status vpn-agent
journalctl -u vpn-agent -n 30 --no-pager
```

Если сервиса нет — агент не установлен. Скопируйте команду из кнопки
**«Установка»** в строке сервера и выполните её под root. Скачивать
`agent.py` отдельно бесполезно: его ставит скрипт вместе с Xray и
systemd-юнитом.

Ту же команду с уже подставленным токеном печатает панель из консоли:

```bash
cd /opt/vpn-panel
.venv/bin/python scripts/node.py install
```

**2. Порт закрыт файрволом.** Проверяется с машины, где стоит панель:

```bash
curl -s -o /dev/null -w '%{http_code}\n' http://<IP сервера>:8443/health   # ждём 401
```

`401` означает, что агент жив и отвечает (просто без токена). Пусто или
таймаут — порт закрыт:

```bash
# на сервере с агентом
ufw allow from <IP панели> to any port 8443 proto tcp
```

**Если панель и VPN — одна машина, всё это не нужно**: укажите в поле
«Адрес агента» `127.0.0.1`, и соединение пойдёт локально, мимо файрвола.

**3. Токен не совпадает.** Панель напишет «агент отверг токен». Значение в
поле «Токен агента» должно совпадать с `AGENT_TOKEN` в
`/opt/vpn-agent/agent.env` на сервере; после правки —
`systemctl restart vpn-agent`.

### Сервер красный: «Конфиг не принят Xray»

Панель показывает то, что сказало само ядро, и дописывает подсказку. Самая
частая причина — **занятый порт**: если панель стоит на этом же сервере,
порт 443 держит её nginx, и подключение на 443 не поднимется.

Выхода два, и выбор не безразличен: REALITY на 443 маскируется убедительнее
(сам Xray предупреждает о других портах), поэтому если VPN важнее админки —
освободите 443 для него, а панель перенесите. Если наоборот — смените порт
подключения в «Подключения» → «Настроить».

Агент сначала проверяет присланный конфиг ядром (`xray run -test`) и только
потом подменяет рабочий. Поэтому ошибка **в самом конфиге** ловится до
перезапуска: Xray продолжает работать на прежнем, клиенты ничего не замечают,
а в панель уезжает точная строка ядра. Ошибки, которые видны только при
настоящем запуске (занятый порт, права на сертификат), ловятся на старте — там
агент откатывается на прошлый конфиг.

Отвергнутый конфиг остаётся на ноде как `/usr/local/etc/xray/config.rejected.json`,
и его можно проверить руками:

```bash
xray run -test -config /usr/local/etc/xray/config.rejected.json
```

**Разбор одной командой на самом VPN-сервере** — проверяет агента, ядро,
вывод последнего запуска, оба конфига и то, кем заняты порты подключений:

```bash
curl -fsSL https://panel.example.com/install/diagnose_node.sh -o diagnose_node.sh
bash diagnose_node.sh
```

Команда есть в панели: «Серверы» → «Установка». Запускать её надо на ноде, а
не на сервере панели.

Что ещё можно посмотреть вручную:

```bash
journalctl -u vpn-agent -n 30 --no-pager
curl -s -H "Authorization: Bearer <токен>" http://127.0.0.1:8443/health
tail -20 /usr/local/etc/xray/xray-stdout.log
```

Поле `output` в ответе `/health` — последние строки вывода Xray. Если оно
пустое, а в панели «xray упал» без объяснений, значит на ноде агент старше
версии 2: он отправлял вывод ядра в никуда. Обновите его.

### Домен не открывается из браузера

Сначала соберите картину одной командой — она проверит сервис, порты, nginx,
сертификат, DNS и файрвол:

```bash
cd /opt/vpn-panel
bash scripts/diagnose.sh
```

Если в отчёте всё зелёное, а браузер всё равно не открывает, смотрите на
текст ошибки — он однозначно указывает на причину:

| Что показывает браузер | Причина | Что делать |
| --- | --- | --- |
| `ERR_TOO_MANY_REDIRECTS` | Cloudflare в режиме Flexible ходит к серверу по http, а сервер редиректит на https | SSL/TLS → Overview → **Full (strict)** |
| Ошибка **521/522** Cloudflare | Cloudflare не достучался до сервера: порт 443 закрыт | открыть 443 в файрволе хостера (в панели VPS, не только `ufw`) |
| Ошибка **526** | Cloudflare в режиме Full (strict), а сертификат на сервере не выпустился | перевыпустить: `certbot --nginx -d <домен>` |
| `ERR_NAME_NOT_RESOLVED` | запись ещё не разошлась или закешировалась у вас | `ipconfig /flushdns`, подождать несколько минут |
| Таймаут без ответа | порт 443 закрыт, а домен идёт напрямую (серое облако) | открыть 443 у хостера |

Проверить со своей машины (PowerShell):

```powershell
nslookup vixar.fun
Test-NetConnection vixar.fun -Port 443
curl.exe -v https://vixar.fun/healthz
```

`curl.exe -v` покажет, доходит ли соединение и кто отвечает — этого обычно
достаточно, чтобы понять, чинить файрвол или настройки Cloudflare.

### Если что-то не встало

**`Failed building wheel for asyncpg / greenlet / pydantic-core`,
`fatal error: Killed signal terminated program cc1`.**
Так выглядит попытка pip собрать пакеты из исходников: готовых сборок под
ваш Python ещё нет, а на маленьком сервере компиляция вдобавок падает по
памяти. Обновите код — версии зависимостей заданы диапазонами и ставятся
готовыми колёсами на Python 3.11 и новее:

```bash
cd /opt/vpn-panel
git pull
rm -rf .venv
bash scripts/install_panel.sh
```

**`pg_lsclusters: not found` при установке postgresql.** Безобидное
предупреждение debconf на минимальных образах Ubuntu — установка идёт дальше.

**Панель не стартует.** Причина почти всегда в первых строках лога:

```bash
journalctl -u vpn-panel -n 30 --no-pager
```

**Обновление кода вручную:**

```bash
cd /opt/vpn-panel
git pull
.venv/bin/pip install -r requirements.txt
systemctl restart vpn-panel
```

При старте панель создаёт недостающие таблицы **и добавляет недостающие
колонки** — обновление схемы руками через `psql` не нужно, данные при этом
не трогаются.

**Обновление агента на нодах.** Агент живёт отдельно от панели, `git pull` в
`/opt/vpn-panel` его не меняет. В колонке «Xray» панель показывает метку
«агент устарел» там, где версия отстала от той, что лежит в панели.

Обычный путь — кнопка **«Обновить агента»** у сервера: панель присылает агенту
его новый код по тому же каналу, которым заливает конфиг, агент проверяет код и
перезапускается. Подключения на этой ноде обрываются на несколько секунд, пока
поднимается Xray.

Агенты, поставленные до появления самообновления, кнопку не понимают — их надо
один раз обновить с сервера тем же скриптом, что и ставили, только без токена
(он возьмётся из `/opt/vpn-agent/agent.env`, Xray не переустанавливается):

```bash
curl -fsSL https://panel.example.com/install/install_agent.sh -o install_agent.sh
PANEL_URL=https://panel.example.com bash install_agent.sh
```

Команду нужно запускать **на VPN-сервере**, а не на сервере панели. Готовая, с
вашим адресом — в панели: «Серверы» → «Установка». Если панель в этот момент
недоступна и скачать нечего, скрипт так и скажет и оставит работающего агента
на месте.

**Резервные копии.** Ценна только база: в ней ключи пользователей, при её
потере придётся перевыпускать все подписки.

Одной командой — база вместе с ключами из `.env`:

```bash
cd /opt/vpn-panel && bash scripts/backup_panel.sh
```

Получится `/root/vpn-panel-<хост>-<дата>.tar.gz`; развернуть его на другом
сервере — `bash scripts/restore_panel.sh <архив>`. Этой же парой делается
переезд панели, см. **[GOLIVE.md](GOLIVE.md)**.

Только база, без `.env`:

```bash
su - postgres -c "pg_dump vpnpanel" | gzip > /root/vpnpanel-$(date +%F).sql.gz
```

Строку в cron — раз в сутки:

```
0 4 * * * su - postgres -c "pg_dump vpnpanel" | gzip > /root/backup/vpnpanel-$(date +\%F).sql.gz
```

Отдельно сохраните `SECRET_KEY` и `SUBSCRIPTION_SECRET` из `.env`: без
второго не проверятся токены подписок даже при целой базе.

## Вариант с Railway

Если не хочется возиться с сервером — панель разворачивается и на Railway
(`railway.json` и `Procfile` уже в репозитории):

1. New Project → Deploy from GitHub repo → `VPNControlPanel`.
2. Add Postgres — `DATABASE_URL` подставится автоматически.
3. В Variables задать `SECRET_KEY`, `PANEL_URL`, `ADMIN_USERNAME`,
   `ADMIN_PASSWORD`, `SUBSCRIPTION_BASE_URL`, `SUBSCRIPTION_PATH`,
   `SUBSCRIPTION_SECRET`.
4. Settings → Networking → привязать домен подписок.

Ноды при этом всё равно остаются на обычных VPS: Railway управляет ими по
сети. Учтите, что агент придётся открыть в интернет (Railway не даёт
фиксированного исходящего IP), поэтому токен агента должен быть длинным,
а `agent_tls` — включённым.
